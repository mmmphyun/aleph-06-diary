## 1. 진행 방식

마일스톤은 단순 일정 구분이 아니라 **검증 가능한 동작과 통과 증거(요청-응답 페어)**를 기준으로 정의합니다.  
각 마일스톤은 기능 완성 선언으로 끝나지 않으며, 네트워크 페이로드, Firestore Rules 거절 응답, UI 상태 전이 등 객관적 증적을 확보해야 완료됩니다.

권장 순서는 다음과 같습니다.

1. **M0 — 인증 방식 결정, 스키마 확장 및 5일 관찰 프로토콜 수립**
2. **M1 — 인증 화면(가입·로그인·로그아웃) 및 다이어리 진입 게이트 구축**
3. **M2 — Firestore 보안 규칙 전면 개편 및 사용자 격리 데이터 마이그레이션**
4. **M3 — 양방향 교차 권한 침투(IDOR) 방어 및 거절 증적 확보**
5. **M4 — 세션 무효화, 토큰 수명 주기 관리 및 자격 증명 보안 점검**
6. **M5 — 5일 실사용 관찰 기록 수립, 3일차 진입 전 규칙 변경 및 지표 대조**
7. **M6 — 인증 구현 설명서 6개 항목 종합 및 최종 제출 패키징**

## 2. 현재까지 확정된 제품·인증·데이터 방향

### 인증 및 권한 격리 아키텍처
- **인증 솔루션:** `Firebase Authentication (Email/Password)` SDK v12.19.0 사용.
- **선택 사유:**
  - 기존 프로젝트 인프라(`Cloud Firestore`, `Firebase Hosting`)와의 네이티브 토큰 연동(`request.auth`).
  - 브라우저에 비밀번호 평문 및 서비스 계정 비밀키를 저장하지 않는 클라이언트 보안 표준 충족.
  - 클라우드 백엔드 수준의 솔트 적용 해시(Modified scrypt) 자동화로 무결성 보장.
- **검토 후 배제한 대안:**
  - 자체 JWT 서버(Node.js/Express): 별도 백엔드 호스팅 비용 및 시크릿 키 관리 취약점 노출 위험으로 배제.
  - Supabase/Auth0: 기존 Firebase 인프라와의 추가 통신 레이턴시 및 이원화된 계정 관리 오버헤드로 배제.
- **비밀번호 관리 메커니즘:**
  - Firebase Authentication 백엔드에 내장된 `scrypt` 기반의 단방향 암호화 해시 적용.
  - 전송 구간은 HTTPS(TLS 1.3)로 보호되며 브라우저 로컬 스토리지, 세션 스토리지, 서버 로그 어디에도 평문 비밀번호를 남기지 않음.
- **인가 및 권한 경계 (Authorization Boundary):**
  - 클라이언트 UI 가림은 보안이 아니며, `firestore.rules`에서 `request.auth.uid == resource.data.userId` 검증을 강제함.
  - 단일 문서 읽기/수정/삭제뿐만 아니라 컬렉션 쿼리(목록 조회)에서도 `request.auth.uid == request.resource.data.userId` 필터링 강제.

### 5일 관찰 기록 프로토콜 (T07 신규 요구사항)
- **관찰 질문:** "계획 대비 실제 소요 시간의 오차율(Time Drift Rate)을 줄이기 위해 시작 시간 고정 규칙을 적용하면 일간 완료율이 향상되는가?"
- **단일 관찰 지표:** 계획 실행 완료율 (Completion Rate)
- **측정 단위:** 퍼센트 (`%`)
- **집계·계산 규칙:**
  - 기본 계산식: `(해당 일자 완료 할 일 수 / 해당 일자 전체 예정 할 일 수) * 100`
  - 결측치 처리: 해당 일자에 계획된 할 일이 0건인 경우 결측으로 처리하며 전체 평균 계산 분모에서 제외함.
  - 중복값 처리: 동일 할 일에 대한 복수 완료 트리거는 T06 멱등성 가드(`runTransaction`)로 1건만 반영함.
  - 이상치(튀는 값) 처리: 하루 계획 할 일 수가 10건을 초과하는 극단적 분할은 본래 단일 작업으로 묶어 1건으로 보정함.
  - 반올림 규칙: 소수점 둘째 자리에서 반올림하여 소수점 첫째 자리까지 표기 (예: 66.67% -> 66.7%).
  - 주 시작 요일: 월요일(Monday)을 주의 시작으로 규정함.
- **계획 규칙 변경 (2일차 뒤, 3일차 앞):**
  - 변경 전 규칙: "마감 시각(23:30 KST) 전까지 완료하면 자유롭게 시작/종료를 기록함."
  - 변경 후 규칙: "할 일 착수 시 반드시 30분 단위 블록으로 시작 시각을 고정하고, 10분 이상 지연 시 사유를 기록함."
  - 변경 시점: 2일차 관찰 기록 마감 후, 3일차 관찰 기록 시작 전 시각을 타임스탬프와 함께 명시함.

### M1 — 인증 화면(가입·로그인·로그아웃) 및 다이어리 진입 게이트 구축

**목적:** 비인증 접근을 원천 차단하고, 960×640px 3D 바인더 물리 인터랙션을 보존한 안전한 계정 등록·로그인·로그아웃 UX를 제공합니다.

- 계정 열거 방어: 존재하지 않는 계정과 비밀번호 불일치 시 동일한 오류 안내 문구 제공 (예: "아이디 또는 비밀번호가 올바르지 않습니다").

### M2 — Firestore 보안 규칙 전면 개편 및 사용자 격리 데이터 마이그레이션

**목적:** 데이터베이스 계층에서 소유자 기반 읽기·쓰기를 강제하고 기존 T06 데이터를 사용자 계정으로 승계합니다.

**작업:**
- `firestore.rules`를 수정하여 모든 컬렉션(`plans`, `tasks`, `logs`, `planHistories`)에 소유권 규칙 적용:
  ```cel
  match /databases/{database}/documents {
    match /plans/{planId} {
      allow read, update, delete: if request.auth != null && resource.data.userId == request.auth.uid;
      allow create: if request.auth != null && request.resource.data.userId == request.auth.uid;
    }
    // tasks, logs, planHistories 동일 패턴 적용
  }
  ```
- 클라이언트 서비스 계층(`src/services/`)에서 모든 문서 쓰기 시 `userId: auth.currentUser.uid` 주입.
- 모든 문서 쿼리 시 `where('userId', '==', auth.currentUser.uid)` 조건 필수 부착.
- **T06 기존 데이터 마이그레이션 (T07-C100)**:
  - 과제 6 프로덕션 DB(`pds-diary-t06`)에 존재하는 실제 데이터(`plans` 2건, `tasks` 7건, `logs` 4건)를 대상으로 일회성 마이그레이션 스크립트를 실행하여 로그인 계정의 `userId`(UID)를 주입함.
  - 마이그레이션 전후 문서 건수 및 무결성을 대조하여 데이터 유실 0건을 입증함.
- **계정 탈퇴 UI 및 데이터 파기 안내 (T07-C134)**:
  - 우측 [보관함(Archive)] 탭 내부 JSON 내보내기 버튼 하단에 [계정 삭제] 버튼 및 "계정 삭제 시 등록된 모든 다이어리 데이터(계획·할 일·실행 기록)가 함께 영구 파기됩니다" 안내 문구를 배치함.
  - 탈퇴 요청 시 `deleteUser()` 호출 및 소유 문서 일괄 삭제(Batch Delete) 처리.

**완료 조건:**
- 미인증 상태에서의 모든 Firestore 읽기/쓰기 시도가 403(Permission Denied)으로 거절됨.
- 기존 T06에 입력된 실제 데이터(계획 2건, 할 일 7건, 실행 기록 4건)가 로그인된 본인 계정으로 온전히 로드됨.
- 보관함 탭에서 계정 삭제 및 데이터 파기 안내 문구가 시인성 있게 확인됨.

### M3 — 양방향 교차 권한 침투(IDOR) 방어 및 거절 증적 확보 [완료]

**목적:** 두 계정을 교차 공격하여 타인의 데이터에 대한 읽기·수정·삭제가 양방향으로 완벽히 차단됨을 입증합니다.

**검증 테스트 스위트:** [src/services/securityRulesIdor.test.ts](file:///c:/work/aleph-06-diary/src/services/securityRulesIdor.test.ts) (12개 전수 통과)  
**거절 증적 보고서:** [docs/t07-idor-defense-evidence.md](file:///c:/work/aleph-06-diary/docs/t07-idor-defense-evidence.md)

**작업 및 검증 결과:**
- 독립된 두 테스트 계정 생성: 계정 A (`user_alpha`), 계정 B (`user_beta`) (T07-C116 확인 완료).
- 각 계정에 고유 계획 1건, 할 일 2건, 실행 일지 1건 생성 (총 8건 격리).
- **방향 1 (A -> B 침투 시도):**
  - 계정 A로 로그인 후 계정 B 소유 문서 ID로 단일 읽기(GET) 요청 -> 403 Forbidden 거절 증적 캡처 (T07-C117 통과).
  - 계정 A로 계정 B 소유 문서 내용 수정(UPDATE) 요청 -> 403 Forbidden 거절 증적 캡처 (T07-C118 통과).
  - 계정 A로 계정 B 소유 문서 삭제(DELETE) 요청 -> 403 Forbidden 거절 증적 캡처 (T07-C119 통과).
- **방향 2 (B -> A 침투 시도):**
  - 계정 B로 로그인 후 계정 A 소유 문서에 대해 읽기·수정·삭제 동일 시도 및 거절 증적 캡처 (T07-C120, T07-C121, T07-C122 통과).
- **클라이언트 트랜잭션 소유권 2차 방어선 (T06-C21 계승 / T07-C126)**:
  - `firestorePlanPackageRepository.executeAtomicTaskStatusTransition` 내부에서 `taskData.userId !== currentUser.uid` 사전 검증을 통해 트랜잭션을 즉시 차단(Abort)하고 예외를 발생시킴을 검증 (통과).
- **위변조 파라미터 테스트 (T07-C123):**
  - 요청 본문에 상대방 UID를 주입하여 생성 시도시 `firestore.rules`에서 403 Permission Denied로 차단됨을 확인 (통과).
- **무결성 및 카운트 불변성 (T07-C125, T07-C126):**
  - 침투 시도 전후 계정 A와 B의 문서 건수(Count)가 각각 4건으로 불변이며, 데이터 유실 0건(100% 무결성) 입증.
  - 거절을 발생시키는 규칙 소스 위치(`firestore.rules` Line 162, 163, 166, 176, 177, 180, 191, 192, 195) 명시 완료.

**완료 조건:**
- A->B, B->A 양방향 읽기·수정·삭제 요청의 실패 응답(403 Permission Denied)이 나란히 문서화됨.
- 공격 시도 후에도 피해 계정의 데이터가 1바이트도 오염되지 않고 건수가 유지됨.
- 목록 쿼리 시 남의 데이터가 섞이지 않음이 확인됨.

**연결 기준:** T07-C116, T07-C117, T07-C118, T07-C119, T07-C120, T07-C121, T07-C122, T07-C123, T07-C125, T07-C126.

- 모든 문서 및 로그 내 토큰/비밀번호 마스킹 유틸리티(`maskSensitiveToken`: `eyJhb...[생략]`) 적용 및 검증 완료 (T07-C115).

**완료 조건:**
